# Optional one-off email look-back

This is separate from standing source reviews. It never enables an ongoing scan or changes existing source settings, cursors, pending messages, review markers or body-read records. It reads Gmail only, in two passes. Drive, past calendars and chat look-back are not part of this flow.

## Consent and coverage

A configured owner in a verified DM can run `/tingle lookback start 7` (choose 1-30 days). The short preview says this is bounded, not full mailbox coverage; selected body text is staged privately for seven days; model picks send short excerpts to the configured model (possibly cloud/billed, with no Tingle cost cap); scan-only makes no model request; nothing is added without individual confirmation; and standing source settings do not change. `/tingle lookback help` carries the full disclosure (numeric caps, MIME bounds, cleanup timing, audit and provider behavior) plus every subcommand. Cancelling reads no account and records no grant. A new explicit start creates a new one-off permission; a completed or failed permission cannot read again.

The first pass lists bounded message IDs, checks each provider `internalDate` against the chosen UTC window before reading headers/snippets, then obtains metadata for eligible messages. Date checks for the listed IDs are read together in one content-free Gmail batch request (IDs and `internalDate` only); headers, snippets and bodies stay per-message. This does not widen consent or change the 100-ID cap. List-Id/List-Unsubscribe headers flag likely list-mail noise. Flagged leads receive no body read. Normal review suppresses only positively automated informational candidates with explicit unconditional no-action wording, or a narrow known receipt/order/shipping/newsletter subject plus known routine boilerplate. Arbitrary text under a routine subject is not enough. Action, reply, question, conditional, unknown-context and incomplete-context cues veto suppression. Unknown languages/context and owner drafts stay visible. This conservative heuristic is not proof of no follow-up and can leave noise visible. Suppressed candidates are saved privately, not deleted or tracked, and remain reachable by ID for the existing retention window. The second pass automatically reads bounded thread context and relevant bodies for other promising leads. It lists thread message IDs first, then date-checks each before its metadata and body; Trash, Spam, Drafts and configured source/ticket exclusions are applied again. Out-of-window replies are not fetched; the context is explicitly incomplete. Full message payloads may include inline MIME attachment parts. It never calls an attachment-download endpoint or follows links; extraction skips filename-bearing parts and retains bounded text only. Inline text prefers plain text over HTML; HTML is returned as untrusted text, never rendered or executed. The Google bridge can refresh its existing local OAuth token. After consent a minimal Gmail getProfile emailAddress read binds the account. Subsequent list, thread, metadata, date and body calls use that exact provider userId, not a mutable me alias. A connection change that cannot access that account fails closed. Only the hashed account identity enters the duplicate-read ledger; hashing is not anonymization.

Headers, snippets and bounded bodies are review leads, not verified commitments or proof that a request is unanswered. The owner must inspect their email if more context is needed. This scan never claims full thread or mailbox coverage: at most 20 thread message IDs per selected thread are examined, and both date scope and shared body budgets can leave gaps. It reports listed IDs, date-checked messages, staged leads, caps/page boundaries and errors separately. Missing or malformed dates, identity mismatches and provider failures do not widen scope or trigger an automatic retry.

The privacy disclosure shown before consent covers Hermes-host storage, the configured model/history/logs/gateway, local OAuth refresh and outside copies. These private slash-command replies still travel through the owner's messaging service and Hermes command/session handling. Private means access-gated within Tingle, not end-to-end isolation from the Hermes host, gateway or operator's configured services. No model tool can list these candidates. The plugin has no built-in Tingle-operated telemetry/content-upload service in the current build; that does not describe the rest of Hermes or providers.

## Private review

The scan start confirmation offers two explicit choices: "Scan + model picks" and "Scan only, no model". Only the first sends anything to a model. Its approval covers that scan's first model run only, is recorded on the private scan row with the assessment version, and is consumed before any content leaves. Scans made earlier never gain it; `/tingle lookback assess LB-ID` asks again for one more run (at most two runs per scan). After either choice, Tingle immediately walks pending leads one at a time in the verified owner DM; nothing is added without the existing item-level confirmation. If a decision times out, the walk pauses and resumes with `/tingle lookback review LB-ID`. If no leads remain, the reply preserves any coverage/model-failure warning instead of claiming an all-clear.

Selection is a bounded judgment by your configured Hermes model (the `ctx.llm.complete_structured` host facade, active model, no provider/model/profile/agent override, no tools), not a keyword ranking. It sees only already-staged private excerpts: at most 72 conversations in at most 6 requests of 12, at most 1,800 characters and 4 messages per conversation, no addresses, links followed, attachments or new mailbox reads. Owner-last conversations with a staged received message can be assessed. Owner drafts remain private and are not sent. Email text is passed as untrusted data inside one JSON value. The answer is validated locally against a strict schema: IDs must be ones that were sent, a pick needs an exact quote of 12 to 200 characters from a message whose author is verified as someone else (unknown authorship never counts; scans made before this version label thread bodies unknown). The quote check proves provenance, not meaning: a real but benign or opposite sentence could be quoted by a wrong answer, so picks stay unverified, resolved or malformed answers never qualify, text is length-bounded and links are stripped. A malformed or unknown-ID response fails the request; two consecutive failed requests stop further requests (no Tingle retry loop), while isolated failures allow later batches and earlier validated picks are kept. Model failure text is never shown or stored. The model cannot add, send, fetch or change anything, and its output is never an approval. There is no fixed result-count target: every pick that passes validation is reachable through `/tingle lookback results LB-ID [page]`, and when none pass, none are shown. Honest limits: this does not verify that a request is still outstanding (history is capped and the model can be wrong), the model call may be billed by your provider and Tingle cannot cap or see the cost (the host may retry or fall back, so one logical request can be more than one provider attempt), and prompts and excerpts can remain in the provider's and Hermes's history. Excerpts keep the newest message and the head and tail of each message; omitted older messages and shortened text are stated to the model and flagged on the pick ("Partial context"). One transaction checks and consumes the approval with a unique run token, so a racing second run sends nothing and cannot clear the first run's marker; a stale run (20 minutes) can be taken over and the old worker then stores nothing. Picks whose staged content changed or that were accepted/skipped during the run are dropped before storing. Result pages are fixed when the assessment is stored and named by an `AS-` ID in every command; a replaced set is refused, never silently re-pointed: handled picks disappear but never move other picks between pages, so a shown continuation stays valid. Stored picks hold only the action and quote and are deleted on accept, skip, discard or expiry.

Use `/tingle lookback list LB-ID [page]` for private grouped review, five conversations per page. `/tingle lookback thread LC-ID [page]` lists every pending candidate ID in that conversation, including older members not selected by the shortlist. Individual view/accept remains available by ID. `/tingle lookback list LB-ID details` shows coverage and counters. `/tingle lookback view LC-ID [page]` shows full staged body/thread context in 4000-character pages. Only the initiating configured owner principal, in a DM on that profile, can access a scan. Subjects/snippets are sanitized, bounded and labeled untrusted. Other owners cannot inherit a scan just because they share profile access. Anyone with OS file access remains inside the existing local trust boundary.

Candidates are stored in a separate `plugin-data/hermes-tingle-lookback` database. Ordinary list/get/model tools, source reviews and snapshots do not query this database. The dedicated read permission is consumed on completion or failure. Full body text is stored only in this private review staging, bounded/truncated as disclosed, until accepted, skipped, revoked or expired. Candidates expire after seven days and cannot be listed or accepted afterward; expired payloads are removed on the next authenticated look-back operation, including help and unavailable/invalid candidate paths. There is no background deletion guarantee at the exact expiry time. Private backups and copies already in history/services may remain.

`/tingle lookback skip LC-ID` dismisses a lead for this scan only and removes its staged content. It does not create a permanent preference. The same email can appear in a new explicit scan. `/tingle lookback discard LB-ID` (or `revoke`) revokes that scan and deletes its candidates only. Existing items, standing source data and grants are untouched. Authenticated initiating-owner revoke remains available after expiry and is idempotent, without restoring read/view/accept access. One-off revoke clears duplicate-read records created by that scan, not other standing-read records; ordinary skip is not revocation. A read already started cannot be recalled; revocation is checked before and after each provider call and before staging.

The original profile, full valid policy, owner and standing-email consent epoch are bound before waiting for a lock. A policy/owner/profile change or standing-email disable/re-enable invalidates old intent. A currently disabled standing source does not bar a separately confirmed one-off grant, but the scan never enables it. Concurrent source changes share the source-operation lock and can wait for the bounded in-flight operation, as existing source revocation does. One-off revoke changes its own state independently, so the next boundary stops it.

## Automatic preparation, explicit acceptance

After the scan and model step, Tingle begins `/tingle lookback review LB-ID` automatically. If a choice times out, use that command to resume. Everything else, including `track-top`, is under `/tingle lookback help`. When picks exist, `/tingle lookback track-top LB-ID AS-ID [page]` remains available there: prepare the still-pending picks of that one fixed results page (omitting page means page 1), never other pages or the whole scan. Tingle proposes title, summary and no-invented-deadline fields and shows the exact shared-profile items before confirmation. No scan, assessment, results page, list, thread view or assistant tool can add an item. All other leads remain staged, not discarded, and are not obligations to work through. An explicitly requested review walk shows one representative per conversation, at most five per invocation; accepting or skipping that representative does not silently change its other members.

Suppressed counts include `/tingle lookback suppressed LB-ID [page]`, which lists private IDs and subjects. `/tingle lookback view LC-ID` opens one and offers the existing explicit accept/skip path. Normal review intentionally excludes suppressed matches, so it is not the recovery route. Suppression learns no permanent rule and changes no source setting. Empty/all-noise completions do not steer the owner into an empty review walk.

Track-all and explicit multi-ID accept allow up to 100 leads, matching the scan's existing maximum, not cross-scan discovery or an unbounded queue. Every exact title, summary and due field is shown before the final Add shared-profile confirmation. Suppressed/skipped/expired/other-scan leads are not selected by track-all. Each item uses the same locked generation/state/draft/policy/source checks; one failed item is reported while others can succeed.

The pinned Telegram control-card sender uses one message, and Discord clips oversized questions. Therefore the exact full-field preview is losslessly split into 1400-UTF-16-unit pages with a short header and choice labels. Only the final page offers Add; Next is navigation, not approval, and cancel or an unexpected answer at any page adds nothing. The advanced track-all path has no five-item cap; it is no longer the default suggestion. A large explicit batch or long edited summaries can still require many Next taps. A displayed results page is transport-bounded, but unusually long edited fields can still require exact-preview pages. It is not fully hands-off bulk approval. Raising page size without a verified surface-specific rendering guarantee or silently dropping fields would make consent unreliable; neither is done here. Runtime source inspection and synthetic page-bound checks are not a live gateway delivery claim.

## Explicit acceptance

```text
/tingle lookback accept LC-ID "Reviewed title" "Your concise summary" "-"
```

Use `-` for no due time, or provide an exact ISO date-time with an explicit UTC offset as the final quoted field. No deadline or unanswered status is guessed. The final confirmation shows the exact fields and warns that the resulting ordinary item is visible to everyone using the profile. Choose **Add this shared item** only after reviewing them. Accept is bound to the candidate ID, one-off generation, current owner/profile/policy/consent epoch and TTL. New accepted references include the verified account hash: `gmail:<account-hash>/<thread>#<message>`. Standing joins, reply checks and completion checks require that same account. Legacy account-unqualified items remain intact but are not silently assigned to any account. An exact same-account collision or legacy unqualified collision is refused; two verified accounts can retain distinct references with the same provider IDs. The scan never reports another account's item as accepted or overwrites it. Review legacy items manually. If a process stops after creating an item but before marking the candidate accepted, retry also refuses the existing collision rather than claiming verified recovery. References are preserved exactly up to 1024 characters; longer references or surrounding whitespace are refused before confirmation/write. No accepted reference is silently truncated.

`/tingle lookback preference "Your reusable tracking rule"` creates a pending preference from your own typed words only. It does not copy source content or approve the rule. A separate `/tingle rule approve FB-ID` is still required. A single skip is never treated as a rule.

## Limits and removal

No live account, original data or real gateway scan was used in repository verification. Coverage evidence is synthetic unless separately stated. No Drive, public-link fetch, attachment download, calendar or chat read is performed by this flow. The operator-local Tingle remover deletes both private look-back and shared-audit namespaces by default, with explicit keep available; it leaves the plugin install and manager record intact. Remove any listed Cron jobs first, run Tingle cleanup with an explicit profile, then run `hermes -p <profile-name> plugins remove hermes-tingle`. Bare native manager removal before Tingle cleanup has no plugin cleanup hook and can leave these directories; see [removal](uninstall.md). Revocation/removal does not erase provider or gateway copies.


## Shared duplicate-read audit and revocation

Both the one-off and standing body paths use the same profile source-operation lock and a shared atomic reservation before a full-body call. A separate `plugin-data/hermes-tingle-body-audit` database stores hashed account/message identifiers, timestamps and a narrow origin label, never subject, snippet or body. Legacy account-unqualified body-read records are consulted conservatively: a matching ID can block a read without pretending to identify which account produced it. Existing standing grants, cursors, pending messages and review markers are not used as one-off state.

While access remains authorized, failed or lost body responses keep their reservation for 14 days, so another flow does not immediately fetch the body again. The UI says recently reserved/read and marks missing context, not that a cached body was recovered. Expired audit rows are ineligible immediately and removed opportunistically during a later claim. Candidate expiry or skipping is not revocation and does not itself clear duplicate-read records.

At the user's explicit choice, revocation clears duplicate-read records rather than retaining an exception: email source revoke clears the shared email audit, and one-off revoke/discard clears that scan's own audit rows. A new explicit opt-in may therefore re-read a body after revocation. Source revoke waits for the current serialized source operation; once it completes, the old operation cannot recreate the ledger. One-off revoke updates the dedicated grant independently, and body claims/staging recheck that generation under a write transaction. Already-started reads cannot be recalled. If secondary audit cleanup fails, revocation reports failure and must be retried; it is not described as fully cleared.

The ordinary standing body path now uses the existing Google bridge with the provider-bound userId rather than the old hardcoded-me body helper. It keeps recent-candidate/source-consent checks, inline text/MIME handling, character limits, error redaction and its existing read ledger, and participates in the shared reservation. Account identity failure occurs before either reservation. These code changes do not authorize actual live access.

## Account and thread-member isolation

Standing email opt-in binds the verified account hash and consent generation. Account switches under the same grant fail closed before content reads and require explicit disable/re-enable. Unknown legacy standing cursors and candidate caches are invalidated before a fresh bounded reconciliation, with an unverified historical-coverage notice; tracked items and shared body-read audit are not reassigned or erased by that migration. Profile, grant and account identity remain checked at source boundaries; requests pin the provider user ID rather than drifting with `me`.

Every thread member is date-, label-, exclusion- and list-header-checked before any full-body call, including context reached through another lead and reused context caches. List-Id/List-Unsubscribe members remain metadata-only independent of scan order. No frequency of real provider ID collisions has been established, and no real account scan is implied by synthetic verification.


## Temporary stage diagnostic

In the owner's DM, run `/tingle lookback trace LB-ID sender-or-subject-words`.
Use at least three characters. Matching is local to the named scan's retained sender and
subject fields, without reading Gmail or calling a model. The reply contains the number
of matching candidate rows and up to 10 private candidate IDs, stage codes and listing
states. It does not repeat sender, subject, snippet or body. These are staging IDs, not
provider message IDs. A matching fragment is not proof that this is the intended message.

Stage codes describe the latest recorded assessment path, not the value of the message:

| Code | Meaning |
| --- | --- |
| `staged` | A row was staged; no later assessment stage recorded yet. An interrupted run can remain here. |
| `suppressed_routine` | Existing routine/no-action heuristic kept the row out of model assessment. |
| `skipped_draft` | A saved owner draft kept the conversation out of assessment. |
| `skipped_owner_last` | Only owner-written messages were staged for the conversation. |
| `capped` | Beyond the conversation cap; not sent. |
| `request_failed` | Its request failed or had an unusable response. No usable verdict saved. |
| `request_not_sent` | Run stopped before its request. |
| `no_valid_verdict` | Request succeeded but this conversation's verdict was missing or invalid. |
| `model_not_action` | Model said possible, not actionable, or already resolved. |
| `pick_unsupported` | Action pick did not pass local exact-quote/received-authorship checks. |
| `pick_changed` | Supported pick's staged content changed before storage. |
| `pick_skipped_by_rule` | An explicit owner skip term removed the supported pick. |
| `pick_listed` | Supported pick stored in the review results. |
| `accepted` | Accepted into tracked items; its private content was cleared, so text lookup no longer finds it. |
| `not recorded` | Earlier row has no stage, or the stored code is unknown. |

Members of an assessed conversation share its code. `lookback list LB-ID details` counts
candidate rows (messages), not conversation totals. No additional content is retained;
codes disappear with their candidate rows at TTL or discard and never enter tracked items
or exports. Handling a candidate clears its searchable payload as before. A later approved
assessment replaces pending candidates' prior codes; the column is not a history of runs.

No match is inconclusive: wrong scan or words, pre-staging filtering/read gaps, cleared
handled content, cleanup or expiry can all explain absence. If the scan itself is unavailable,
the command refuses it. Pre-staging omissions have no row and stay aggregate-only. The old
deleted run cannot be explained. No model prompt, approval version, limits, live scan or
expiry/reminder timing changed.


## Expiry suggestions

Expiry suggestions record three claim fields: a verbatim date span, the model's normalized date reading and its belief that the expiry belongs to this open step. These are unverified claims, not schedule instructions. Old unused grants cannot authorize the new schema; completed imports/results are untouched. No extra model call or mailbox read is made. The qualification schema also includes topic and contextual review-plan fields.

Both individually reviewed acceptance and onboarding support automatic clear expiry timing. Onboarding reports uncertain claims without setting timing or adding questions. A missing or unusable claim leaves today's behavior. Clear claims can be automatic only when all code checks hold: an exact span in a validated received-message quote; one complete ISO or supported English/German full-month-name date with year; no other date-like span, negation/correction/start/conditional marker or clock/zone token anywhere in the model's staged excerpt; complete supplied context; matching model reading and own-item attribution; date after the evidence message and 2-45 local calendar days ahead. Clock/zone claims, invalid or partial dates and out-of-window dates do not get an invented default. A model can still misattribute a clean date; automatic means form checks passed, not verified meaning. The 45-day horizon is a chosen bounded heuristic, not an empirical claim about typical validity periods.

A parseable uncertain claim offers one separate yes/no/another-time/cancel question before acceptance clears its candidate payload. The quote and exact proposed instant are shown, marked unverified. The candidate, all assessed group members, assessment version, source generation, policy/consent, TTL, draft revision and owner binding are rechecked. The item import was independently approved: a no, cancel, timeout-like unexpected response or correction to timing does not reject it. Another-time resets the decline streak and explains the explicit offset-time command after import. A racing source/draft/authority change refuses stale acceptance rather than creating an unbound record. The accepted candidate payload is cleared. Sibling leads in the same thread may retain shared excerpts until their scan expires or is discarded.

The queue is additive. It never writes `due_at`, `next_check_at`, counts, cycle, revision or any ordinary item field. Creation checks current ordinary state, refuses real due-date and reply-watch items, and does not depend on the ordinary next check or remaining attempt budget. Automatic date-only timing is 10:00 owner-local on the day before the unverified date. Its eligibility window ends at the start of that source date, a scheduling heuristic, not an established expiry cutoff. Confirmed instants (including yes to an uncertain proposal) have 45 minutes of grace instead. IANA rules at the target date are used, not a stored UTC offset; folded or missing wall times are refused, including unusual non-night transitions. The existing 30-minute poll is unchanged. A record is eligibility, not a delivery promise.

Pending metadata in the private profile store: item id, fire instant, normalized source date, inferred category, tier, pending state, creation time, eligibility-end and maximum-expiry time. The source-derived date is new retained metadata, not content-free. It can outlive seven-day staging/discard, but is removed on emission/drop, completion/dismissal, item deletion, snooze past fire time or a due/reply-watch change, and never remains eligible beyond its bounded window or maximum 45-day TTL. Physical cleanup is lazy on the next local store operation (including ordinary commands), not an exact background erasure guarantee. A separate emission log contains only item id, attempt time, reserved state and the same expiry time, not the derived source date; it records one attempt before output and persists until that TTL or item deletion. There is no automatic retry after an unknown/failed flush and no ordinary attempt advancement. The nudge never promises a staged-thread view: the accepted payload is cleared, but sibling leads may retain shared thread excerpts until scan expiry or discard. It says the date is unverified, cutoff time unknown and original email should be checked; shared thread excerpts may remain in sibling leads. If an explicit instant lands on/after the source date, wording says it may already have expired.

Derived dates stay out of ordinary item records, exports and item-history views. Nudge/command text still goes through configured gateway and session history; provider/Hermes copies of model inputs/outputs and backups may remain under existing host disclosure.

### Editable expiry preferences

Private applied state is `plugin-data/hermes-tingle/hermes-tingle-preferences.json`, never committed to the repository. Its exact schema is:

```json
{"version":1,"rules":[{"id":"OWNER-vouchers","text":"suppress voucher expiry suggestions","category":"vouchers","origin":"explicit","approved_at":"","action":"suppress"}]}
```

Categories are `vouchers`, `returns`, `trials`, `other`; actions are `suppress` or `resume`. At most 20 file entries with unique ids and text up to 200 characters. All rules in this owner file are explicit. The plugin never writes, renames or deletes the file, including on approval, dismiss, reset or an owner command. Thus a plugin preference write cannot overwrite an external editor save. It rereads the file on every use. Invalid schema, oversized/non-regular/symlink files refuse expiry suggestions loudly without touching ordinary tracking/reminders. A concurrent user save may affect the next check rather than an in-flight check, but the plugin cannot destroy that save.

Applied precedence per category is: last matching owner-file entry, then latest approved explicit owner-command DB rule, then approved learned DB rule. File `resume` overrides learned or command suppression. Owner-command rules carry structured action/category provenance in the existing feedback table; they never interpret arbitrary rule text as a command. The applied-rule list labels all three sources. Copying a learned rule into the user file makes that owner-authored copy authoritative and reset never touches it. To remove a file rule, edit the file; dismissing its DB counterpart does not change the file.

Three consecutive explicit no answers in one inferred category create one visible pending feedback candidate, never silently active. Yes/correction resets that category, silence/cancel/item skip does not count, and category attribution can be wrong. Store metadata is one bounded counter, last prompt fingerprint and suggestion flag per category, not source text or an answer history. Learned applied state and approval provenance share the existing feedback table. Suppressions retain rule id/category/last suppression time for at most 45 days. No plugin-owned sidecar or digest is needed to reconcile the owner file.

Commands (owner DM only):

- `/tingle expiry cancel HT-ID`: remove only the extra pending one-off.
- `/tingle expiry at HT-ID 2026-12-01T10:00:00+01:00 2026-12-02`: choose an explicit offset instant and unverified source date, within the same 45-day bound, independently of ordinary timing. Replaces a pending extra one-off, never resets ordinary attempts. Overrides category suppression for that item; cannot reset an already attempted one-off.
- `/tingle rule add expiry vouchers suppress` or `resume`: explicit category rule in the DB, clearly labeled and always subordinate to the owner file. A resume rule overrides learned suppression.
- `/tingle rule approve FB-ID` and `/tingle rule dismiss FB-ID`: activate/remove a learned expiry preference through the existing owner decision path.
- `/tingle rules reset learned`: dismiss learned DB approvals and clear decline streaks. Owner-file rules and explicit command DB rules remain untouched.

Suppression affects only this feature's new suggestions, including still-pending automatic nudges; ordinary items, visibility, due dates, checks and other categories are untouched. Explicit per-item timing requests still work. Semantic attribution is unmeasured; synthetic tests cannot show how frequently a real model picks the wrong date. Premature/spurious nudges, missed benefit and wanted suggestions hidden by mistaken categorization remain possible. No coverage or delivery guarantee.

Ordinary reminder collisions do not discard an expiry suggestion. The same outgoing message includes the expiry line alongside the ordinary reminder. The expiry reservation still uses its separate attempt log and never advances ordinary attempts. A clear claim 30 days out creates its day-before one-off even if ordinary checks happen first or the ordinary ladder ends.

Document validity windows use the configured date-only time and timezone for YYYY-MM-DD, normalized to UTC for comparisons. Invalid/ambiguous local instants are refused, never compared as raw strings.
